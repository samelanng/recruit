## 运行



- 直接问一个问题

python main.py -question "问题"

- 调整检索条数 / 切分长度 / 重叠长度 / Embedding 后端
python main.py -q "问题" --topk 3 --chunk-size 300 --overlap 60 --backend api


参数说明：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--topk` | 4 | 检索并交给模型的文本块数量 |
| `--chunk-size` | 300 | 每个文本块的目标字符数 |
| `--overlap` | 60 | 相邻文本块的重叠字符数 |
| `--backend` | `auto` | `auto` / `local` / `api`，Embedding 后端 |
--------------------
## 实现说明
程序按 RAG 的标准四步组织，函数与步骤一一对应：
| 函数 | 对应步骤 | 做法 |
| --- | --- | --- |
| `load_documents()` | 加载 | 读取 `knowledge_base/` 下 4 个 `.md`，跳过 macOS 的 `._*` 元数据文件，保留来源文件名 |
| `split_documents()` | 切分 | 先按段落聚合，每块约 300 字，相邻块重叠60字；超长段落按窗口硬切 |
| `build_index()` | 建索引 | 把每个文本块转成向量，L2 归一化后存在内存里的 numpy 矩阵 |
| `retrieve()` | 检索 | 问题向量与所有文本块向量做点积（等价余弦相似度），取 Top-k |
| `generate_answer()` | 生成 | 把「问题 + 检索到的文本块」发给 `qwen-plus`，要求仅依据资料作答 |

### Embedding 后端
- local：`BAAI/bge-small-zh-v1.5`
- api：阿里云百炼 `text-embedding-v3`
- auto（默认）：优先用本地模型，导入失败时自动回退到 API
本次测试使用的是：api:text-embedding-v3

### 生成用的提示词
`system` 消息负责定规则，`user` 消息里放「资料+问题+回答要求」：
```
你只能依据用户提供的资料回答问题，禁止使用任何资料以外的知识……
资料：
【01_overview.md】……
问题：……
回答要求：
1. 只依据上面的资料作答，不要补充资料中没有的内容；
2. 如果资料无法回答该问题，只输出"资料中未提及"；
3. 回答控制在 150 字以内；
4. 最后按格式列出实际用到的文件名。
```

### 输出格式
```
回答：xxxxxx
参考资料：
- xxxx.md
```
程序会先打印检索结果（每个文本块的来源文件名、相似度、内容预览），
再打印最终回答，便于验证答案确实来自资料库。

## 思考题
1. RAG 中的“检索”和“生成”分别在做什么？
检索负责找资料：把知识库切成文本块、转成向量，再根据问题的向量找出最相关的几块，它决定了模型能看到什么。
生成负责写答案：大模型拿到问题和这几块资料后，把分散的信息组织成通顺、直接的回答。
2. 为什么不直接将所有资料一次性放入提示词？
- 是长度和成本：资料一多就会超出上下文窗口；
- 效果：无关内容会稀释注意力，模型更容易抓错重点，也更容易把资料外的知识混进来；
- 可扩展性：资料更新只要重做索引，不必重新组织一整段超长提示词。检索把全部资料变成
和这个问题最相关的一小部分。
3. RAG 与模型微调有什么区别？
- 微调是把知识写进模型参数，需要训练数据和算力，成本高、周期长，而且知识更新后要重新训练。
- RAG 是把知识放在模型外部，只在提问时把相关片段送到提示词里，改资料只要重建索引，几分钟就能生效。
微调更适合改变模型的风格或能力，RAG 更适合让模型回答特定资料范围内的事实性问题。
4. 如果检索到的文本与问题不相关，最终回答可能会出现什么问题？
- 编造，模型为了回答问题而用资料以外的知识补全，产生幻觉；
- 答非所问，把无关资料里的内容当成答案；
- 给出一个看似确定的错误答案。
